## P0-A｜字节逐张量复算

### 要解决的问题

`results/p202/results.json` 里 `base=0.140625`、`asym_sign=0.24609375`、`aligned=0.265625`、`k4v4=0.40625`。前三个能由 (data+meta)/32 复算，第四个不能。**必须给出每个配置的逐项字节表，并解释 k4v4 的差异来源。**

### 步骤

1. 读 `VisContract_P14_2/scripts/p201_refinement.py:quantize()`、`p202_refinement.py:pack/augment`，确认：
   - 组大小（已知 128）
   - 每组元数据（已知 `scale` + `minimum` 两个 fp16 = 32 bit）
   - 打包是否按 bit-plane、是否要求 `numel % 8 == 0`
2. 对每个配置，逐层逐张量累加：
   - `data_bits = numel × bits`
   - `meta_bits = n_groups × 32`
   - `padding_bits`（对齐补零）
3. 分母取**该模型视觉 token 的 FP16 K+V**，逐层核对（不是全模型、不是单张量）。
4. 与 `results.json` 的 `payload_ratio` 比对。

### 输出 schema

```json
{
  "model": "InternVL3-8B",
  "denominator": {"scope": "visual_kv_fp16", "bytes": 0, "layers": 0, "tokens": 0},
  "configs": [
    {
      "name": "asym_sign",
      "accounting": "deployed",
      "per_layer": [{"layer": 0, "k_data": 0, "k_scale": 0, "k_zero": 0,
                     "k_residual": 0, "v_data": 0, "v_sign": 0, "v_alpha": 0,
                     "padding": 0}],
      "total_bytes": 0,
      "ratio": 0.24609375,
      "ratio_reported": 0.24609375,
      "delta_pp": 0.0
    }
  ],
  "k4v4_explanation": "…"
}
```

### 验收

- `asym_sign`、`aligned`、`base` 三者 |delta| < 0.5%。
- `k4v4` 的 40.6% 被**明确解释**（预期：payload = base + K4V4，非独立部署）。
- 分母可被第三方用同一脚本复算。

### 失败处理

若 `asym_sign` 也对不上：优先查 (a) 是否包含 `minimum`，(b) 组大小，(c) 分母是否含非视觉 token。三者排除后仍不符 → 说明旧结果不可复算，**P202 的质量结论一并降级**。

## P0-B｜基线同语义复现

### 要解决的问题

FP16 / KIVI2 / native4 是否真在同一执行语义下（同 prompt 模板、同 generation config、同 cache 布局、同 graph 开关）。

### 步骤

1. 选 60 个会话（GQA grouped，图像级切分，与标定集不重叠）。
2. 三个基线各跑一次，greedy，固定 `max_new_tokens`。
3. 记录：首 32 token 的 id 序列、EM、TTFT、TPOT。
4. 与历史记录（`results/p38_*`、`results/p201`）对比。

### 输出 schema

```json
{"sessions": 60, "model": "InternVL3-8B",
 "methods": [{"name": "fp16", "em": 0.0, "em_hist": 0.0, "delta_pp": 0.0,
              "first32_match_hist": true, "ttft_ms": 0.0, "tpot_ms": 0.0}],
 "semantics": {"prompt_template": "…", "generation": {"do_sample": false, "max_new_tokens": 0},
               "graph": "on|off", "cache_layout": "…", "quant_position": "after_visual_prefill"}}
```

### 验收

- FP16 与历史 EM 差 < 0.5pp。
- greedy 下首 32 token 与历史完全一致（不一致 → 执行语义变了，后续所有比较作废）。
- 三个基线共享同一 `semantics` 字段。

## P0-C｜编码可复现

### 步骤

1. 用 `p202_refinement.py` 的 `augment()` 重跑 4 组 CLEVR 开发对话。
2. 对比 `correct=24`、`repaired=3`、`new_errors=0`、`attention_error=0.03067215`。

### 验收

- `correct` 完全一致；`attention_error` 相对误差 < 1e-3。
- 若不一致，定位到：模型权重版本（GPTQ-Int4 vs BF16）、`dtype`、组大小、`minimum` 是否存在。

### 注意

这一步只验证"能复现"，**不验证"结论成立"**。n=36 的结论在 P1/P2 才重做。

## P0-D｜执行路径审计

### 要回答的五个问题

1. 量化发生在哪一步？（视觉前缀 prefill 之后？写回缓存之前？）
2. 后续轮新增文本 token 时，视觉前缀是否被重新计算？（应为否）
3. 三个阶段在代码中的函数入口分别是什么？
4. 缓存里实际驻留了哪些张量？（base / residual / sign / alpha 是否全在显存）
5. CUDA graph 覆盖了哪些 kernel？量化/反量化是否在图内？

### 产出

`audit/code_audit.md`，含：

- 调用链（函数名 + 行号）
- 一张数据流图（文本描述即可）：图像 → visual tokens → prefill → 量化 → 写缓存 → 后续轮读取 → decode
- "哪些是模拟、哪些是真实测量"的逐项标注

### 验收

能明确回答：**阶段分离到底能省什么**（存储？读带宽？都不省？）。

> 当前预期：只省读带宽，不省存储（ERRATA E3）。若审计发现连读带宽也不省，分支 2 直接取消。
