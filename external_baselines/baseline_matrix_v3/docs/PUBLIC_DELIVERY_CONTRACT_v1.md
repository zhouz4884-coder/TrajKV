# External baseline increment delivery

The public destination is the existing `zhouz4884-coder/TrajKV` repository under `external_baselines/baseline_matrix_v3`. Existing Round1–8 commits, tags, releases and assets remain intact. This document describes preparation; neither an exporter receipt nor a local Git commit proves that GitHub received an increment.

`python ops/export_public.py --stage NEW_NAME --phase p1` prepares a reviewable preview on the named E evidence volume. `--require-complete-phase` additionally requires every row of the frozen core matrix to have its original three raw files, complete expected coverage, PASS status and a unique complete offline score summary. A new stage name is required after any change. The exporter never opens a credential helper, connects to a server, invokes Git or writes to earlier project/evidence assets.

Public payloads include the method/model/metric source and source locks, licenses, declared configuration, selected P0 technical evidence, the relevant phase's raw result mirror, offline scored evidence and browsable tables/reports. Original images, model weights, tensor dumps, compiler caches, private SSH/control/download operations, private execution checkpoints, private chat and machine connection information are excluded. Raw mirrors, archives and staging use `${EVIDENCE_ROOT}`; canonical inference assets remain on the remote data volume. D stores only small source and report files.

Paths inside selected JSON/JSONL and text are rendered as `${DATA_ROOT}`, `${DATA_DISK}`, `${PROJECT_ROOT}`, `${EVIDENCE_ROOT}`, `${FROZEN_TRAJKV_ROOT}` or home templates. Public raw evidence is therefore explicitly derived. Original hash fields retain their meaning as source identities; they are not silently rewritten into hashes of sanitized files. `PUBLIC_CONTENT_REFS.json` binds each original source SHA256 to its exact public-archive SHA256, LF-normalized Git SHA256 and Git blob OID. Per-line source/public fingerprints bind scored rows to their original raw record identities. Prediction text, reference answers, token IDs, source IDs and numeric measurements are not edited to improve scores.

The exact-byte archive contains the full selected public payload. Git carries browsable code/configuration/tables and small manifests; large `records.jsonl` and `scored_records.jsonl` remain archive assets. Source byte guards can require CRLF checkout bytes, so use the exact-byte archive when rerunning those guards. Git's `.gitattributes` LF conversion is separately audited and is not treated as changed experimental output.

Cold verification uses `python ops/verify_public_export.py --root ${EVIDENCE_ROOT}/public_staging/NEW_NAME/tree/external_baselines/baseline_matrix_v3 --archive ${EVIDENCE_ROOT}/public_staging/NEW_NAME/NEW_NAME.zip --recompute-scores --receipt NEW_RECEIPT.json`. It checks every indexed body, archive member, Git LF fingerprint, per-line identity, original raw SHA graph, expected QA coverage and score-to-original-output binding. It independently recomputes all available scored means and source-cluster confidence intervals from the published frozen references. The generated public helper is available at `code/verify_public_export.py` in the exported namespace. It requires Python and NumPy, no GPU, model, image or server access.

The publisher must inspect the actual intended Git account and repository, preserve the previous remote head/history, add exactly the index's `expected_in_git` set plus the index, and verify the actual staged/committed tree and blob bodies. Reference and source manifests are explicitly force-added if ancestor ignore rules match them. Publication is an ordinary history-preserving increment, never a force rewrite. Release assets must match the prepared archive/index SHA256; the final receipt binds a fixed commit/tree, index blob OID and exact archive SHA256. Independent remote ref/tree/body checks and asset identities are required before reporting upload success. A transport failure remains an unfinished external delivery, not a completed upload.

P1 is a fixed-source subset comparability stage. Its table is never labeled a full official split. P0 arithmetic/native hardware controls remain technical evidence, separate from benchmark scores. Instrumented prototype wall time is separate from a controlled-speed comparison. Subsequent P2/P3 increments must also include the provenance dependencies of any reused-prediction views before publication.
